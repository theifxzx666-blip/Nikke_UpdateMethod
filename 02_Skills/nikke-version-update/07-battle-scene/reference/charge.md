# 多判充能点

## 一、只看一件事：一枪能穿几件

```
一次攻击的爆裂充能 = 命中件数 × per_shot
```

充能与「一枪穿几件」成正比，**与伤害无关**。所以问题化简成：
在某个阵位、某个瞄准角下，射线能穿过多少个不同的可穿透物体。

## 二、两个等价分支，算法不同但结论应一致

| 分支 | 做法 | 判据输出 |
| :--- | :--- | :--- |
| **角度枚举** | yaw × pitch 网格（步长 0.25°）逐条打射线，数穿过的件数 | `rad[j,i]` 矩阵 |
| **像素枚举** | 在 1600×900 的实机投影画面上逐像素反投影成射线 | `n_1deg` 计数 |

`scan_charge_points.py` 走角度枚举；ChargeMap 的 `scan_px.py` 走像素枚举。
**两者可以互相校验**：同一阵位 Top-1 点位应落在同一世界位置。

## 三、遮挡规则（错一条就会虚高）

| 规则 | 说明 |
| :--- | :--- |
| 可穿透档位 | 只有 `soft` / `medium` / `hard` 计段数 |
| 遮挡物 | `ground` / `static_object` / `cover_object` 命中距离 < 目标距离时，**该目标作废** |
| 自家掩体 | `cover_object` **既不计段数，也挡视线** |
| 不穿透档位 | `noncol_object` 完全忽略（不挡也不算） |

`*_col` 地形碰撞网格必须**事先滤掉**，否则射线在第一米就撞上隐形地板，全部归零。

## 四、1° 窗口换算（最容易错的一步）

@1600×900 / 纵向 fov 60：

| 方向 | 换算 | 1° 对应 |
| :--- | :--- | :--- |
| 横向 | **26.67 px/°** | ±13.3 px |
| 纵向 | **12.51 px/°** | ±6.3 px |

所以「±1° 窗口」= **±13.3 × ±6.3 像素的椭圆**，不是 `±R px` 的方框。

把两者当等价，点数会虚高。判据代码里要分别用 `PX_PER_DEG_H` 与 `PX_PER_DEG_V`。

## 五、角度域 vs 像素域 —— 错的是假设，不是角度这个量

早期结论「准星角 ≠ 枪口角，所以角度法不可信」是**错的**。实测反算：

```
yaw 4.75° / pitch 3.5°  ↔  pixel [799.6, 450.4]
相机 (-4.8, 0, 0)，枪口 (-6.0, -0.89, 4.5)
交点纵深 t = 18.83 m，回代 pitch = 3.50°
横向视差 atan(1.2 / 14.33) = 4.79°  vs 实测 127.1 px ÷ 26.67 = 4.77°   差 0.02°
```

结论：**两个域是同一映射的两个方向**。真正的错误假设是「准星角 = 枪口角」，
枪口相对眼点有横向偏移，所以要用「眼点 → 世界点」投影，不能直接把枪口角当准星角。

## 六、与 ChargeMap 的口径差异（必须写清，避免被当成同算法）

| # | 差异 | 说明 |
| :-: | :--- | :--- |
| 1 | json 短键 vs 长键 | 他们 `g/n/v/i`，我们 `root/name/v/tri` |
| 2 | 相机俯角来源 | 他们由运行时 Cinemachine 驱动（**未实证**），我们没有 `Camera` 组件，走默认 fov 60 |
| 3 | 像素窗口 | 他们按 `±R px`，我们按 `1°` 椭圆 |

前两条决定了**两边的段数不能直接对号**；只有 Top-1 的世界位置可以互相验证。

## 七、密度按区域成套，可作合理性上界

| 区域 | 可破坏物总数 | 档位构成 |
| :--- | --: | :--- |
| 沼泽 | 75~220 件 | soft 较多 |
| 母鲸 | 63~65 件 | **soft 全 0** |
| cityforest | 10~30 件 | hard 各仅 1 件 |

如果算出来某个阵位的可穿透件数超过该区域总数，一定是遮挡规则错了。

## 八、产物

```
charge_multi_<场景>.json    逐阵位 Top-K 点位（世界坐标 + yaw/pitch + 命中件数）
charge_multi_<场景>.tsv     业务表：阵位 / 排名 / 像素 / 角度 / 件数
<场景>_s<n>_充能.png        图上的落点标注
```

`15_收益汇总` 与报告里报数只认这两张表，不另算。
