## 七、结论

### 7.1 判新增：口径要「公告 ∩ 包内新增」，不能只用 diff

| 做法 | 结果 |
| :--- | :--- |
| 只用 diff | 会把莉可丽丝联动、21 个预埋角色、马斯特时装的抽取 UI 全算成「本期新增」，直接违背铁律 3 |
| 只用公告 | 拿不到键、拿不到体量、判断不了哪些立绘真正下发 |
| **两者相交** | 公告 38 条里有 **18 条 ✅ / 9 条 ⚠️ / 11 条 ❌**，剩下的包内新增全部标为预埋 |

### 7.3 更正：「立绘不在缓存里」这句话作废

上一版报告写「全量 12,296 个 `__data` 搜 `icons-char-full` 命中 0」，据此断言立绘没下载。
**这个结论不成立，方法本身是错的**：

1. 缓存路径 `UnityCache/Shared/<hash1>/<hash2>/__data` 里，两级目录都是哈希，
   `<hash1>` 等于 bundle **内部的 AssetBundle 名**（实测 `s01.bundle` → `b5ab855f8872cb5be0a5797ed26b6780.bundle`），
   而**全 46 份 catalog 明文搜这个哈希，一个都不命中**。
2. bundle 里的 container 路径也是裸哈希（`s06.bundle` → `57358fd32367e394a9a7944569e8970a`），**不含键名**。
3. `UnityFS` 块是 LZ4 压缩的，**raw grep 连明文资源名都看不到**（`grep -a c162_01_skillcut` 在已确认含该资源的 `s04.bundle` 上也是 0 命中）。
4. `__info` 只有 4 行文本：`-1` / unix 时间戳 / 文件数 / `__data`，**没有 URL**。
5. `.cat`（`ja.cat` 1,165 行 / `main.cat` 189 行）只管 `.nab` 与静态表，**不含 bundle 的路径与大小**。

所以「缓存里有没有立绘」目前**没有便宜的判定手段**。可读的只有**内部资源名**（`c162_01_skillcut.atlas` 就是这么找到的），
要判定就得用 UnityPy 逐个解包 12,296 个文件——本轮没做，留作下期第一件事。

**现状定性：立绘是否在本地，未知。** 不要再引用「命中 0」这个数。

## 八、下期国服对齐的固定动作

```
① 拿公告（B 站 / 官网），把「新增」条目逐条编号（1.1、2.1、4.1 …）
② 用 01_本期键变化.tsv 逐条找专属新增键族
③ 三档判定：✅ 有专属新增 / ⚠️ 只有变更或只有文本 / ❌ 无客户端证据
④ 剩下所有包内新增 → 一律进「预埋」栏，不进交付
⑤ 交付出表时明确写「本期 N 条 ✅，预埋 M 项已排除」
```
